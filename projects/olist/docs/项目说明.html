Olist 订单履约风险监控与异常跟进平台

1. 项目定位

面向履约运营、客服组长和一线跟进人员的 B 端数据产品。使用 Olist 公开交易数据，完成数据建模、延迟风险识别、订单优先级策略、运营界面和客服记录。它是课程/个人项目的可运行原型，未作为 Olist 官方或真实商业系统上线。

2. 业务问题与用户任务

场景假设：在待送达订单较多、履约信息分散时，工作人员需要先知道异常集中在哪里，再确定先跟进哪笔订单，并让后续人员看到处理进展。未将此假设表述为经过真实用户访谈验证的需求。

  • 履约运营/客服组长：监控逾期、临近到期、高风险订单，按地区和商家定位异常。
  • 一线客服：筛选与搜索订单，查看配送时间线、风险及金额，填写状态和备注。
  • 产品目标：提高异常信息可见性、支持明确的订单跟进顺序、保留处理历史。

3. 用户流程与核心方案

查看整体情况 → 定位异常 → 筛选/排序队列 → 查看订单详情 → 更新客服状态和备注 → 后续人员查看历史。

优先级：已逾期 → 两天内到期 → 高风险 → 其他待送达。相同类别再按逾期天数降序、预测风险降序、订单 ID 稳定排序。

At risk：在当前日期/地区的待送达订单中，风险达到第 80 百分位，且不属于已逾期或两天内到期。它与评价时“每天选前 10%”是不同口径。

4. 产品判断与取舍

  • 已发生异常优先于预测预警，避免高风险概率掩盖已逾期的订单。
  • 保留日期、状态、阶段、金额、地区、配送时间线等工作信息；不在运营详情放入 SHAP。
  • 第一版实现完整跟进链路，不扩展到自动改物流、客服人力调度或绩效管理。
  • 客服记录采用追加事件，避免覆盖旧备注；当前没有客服身份字段，不能称为完整的人员责任审计系统。
  • 单商家订单建模便于归属履约主体；有预测的订单不代表所有订单。

5. 数据与系统

MySQL 21 张表：14 张源数据表、5 张辅助表、predictions、case_events。

Python 通过 SQL 提取审核时已知的 16 个特征，用 CatBoost 预测延迟概率。按时间划分训练和测试数据；送达时间仅用于标签、评价和历史状态，不能进入审核时预测输入。

预测结果写回 predictions，order_id 唯一关联 orders。前端通过 Python API 查询订单和概率；客服操作追加到 case_events。离线展示版改用 SQL 导出的固定数据快照，并在浏览器本地保存演示记录。

6. 已有结果

测试集 18,739 笔订单，实际延迟 717 笔。每天约选 10%，共选 1,915 笔。

相同规模下，风险优先的延迟捕获量约为随机的 2.23 倍。金额优先是离线分析对照，当前运营队列不按风险金额排序。

这些数据只证明选单效果，没有证明客服介入降低了延迟率、节约了人力或提高了满意度。

7. 下一步验证

邀请客服或运营人员进行任务测试，记录异常定位耗时、操作错误与跟进记录完整率。通过真实业务试点再比较异常响应时长和最终履约结果。上线前需要补充登录权限、责任人、日志、数据刷新和运行监控等能力。
